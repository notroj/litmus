# RFC 4918 normative requirements

Itemised MUST/SHOULD requirements extracted from RFC 4918 (*HTTP Extensions for
Web Distributed Authoring and Versioning*), for cross-referencing against
_litmus_ test coverage. See [RFC4918-coverage.md](RFC4918-coverage.md) for which
of these _litmus_ currently tests.

## Scope

This list covers **server-side requirements that a black-box HTTP client can
verify**, since that is what _litmus_ is. Deliberately excluded:

* Client-directed requirements ("a client MUST submit a Depth header ...") —
  they constrain _litmus_ itself, and appear here only where the server has a
  corresponding obligation to enforce or tolerate the behaviour.
* Requirements on internal server behaviour with no observable effect on the
  wire.
* §2 (notational conventions), §21–§25 (IANA, references) and the appendices.
* Umbrella requirements that merely restate the whole document, such as §18.1's
  "a class 1 compliant resource MUST meet all MUST requirements in all
  sections".

Each item has a stable ID of the form `<section>-<n>`, numbered in document
order within the section, so the coverage document can reference it without
quoting the text. The level in parentheses is the literal RFC 2119 keyword used.

Note that a requirement being listed here does not mean it is *practical* to
test — several (lock timeout expiry, ETag reuse over time, partial-failure
behaviour during a deep COPY) need either long runs or a server that can be made
to fail on demand. The coverage document records those as untested with a note,
rather than silently dropping them.

## 4. Data Model for Resource Properties

- **4.1-1** (MUST) All instances of a given live property must comply with the
  definition associated with that property name, including its value syntax.
  This is what makes the `Value:` productions in §15 normative. RFC4918§4.1
- **4.3-1** (MUST) Servers must preserve, in storage and transmission of dead
  properties, the XML Information Items listed in the section — element names,
  attribute names and values, character data, and namespace declarations.
  RFC4918§4.3
- **4.3-2** (SHOULD) Servers should preserve XML namespace prefixes for any
  Information Item in a dead property value. RFC4918§4.3
- **4.3-3** (MUST) Servers must ignore the `xml:space` attribute if present and
  never use it to change whitespace handling; whitespace in property values is
  significant. RFC4918§4.3

## 5. Collections of Web Resources

- **5.2-1** (MUST) A collection must contain at most one mapping for a given
  path segment. RFC4918§5.2
- **5.2-2** (MUST) For WebDAV-compliant resources A and B with URLs "U" and
  "U/SEGMENT", A must be a collection containing exactly one mapping from
  SEGMENT to B. RFC4918§5.2
- **5.2-3** (SHOULD) Where a server handles a request for a collection named
  without a trailing slash as if the slash were present, it should return a
  `Content-Location` header giving the URL ending in "/". RFC4918§5.2
- **5.2-4** (SHOULD) Wherever a server produces a URL referring to a collection,
  it should include the trailing slash. RFC4918§5.2
- **5.2-5** (MUST) Where a server treats a set of path segments as equivalent
  (e.g. case-insensitive URLs), it must expose only one preferred segment per
  mapping, consistently chosen, in PROPFIND responses. RFC4918§5.2

## 6. Locking

- **6.1-1** (MUST NOT) A server must not create conflicting locks on a resource;
  an exclusive lock conflicts with any other lock, direct or indirect.
  RFC4918§6.1
- **6.1-2** (MUST NOT) A resource added to a depth-infinity locked collection
  must not already hold a conflicting lock, and must become indirectly locked by
  that lock. RFC4918§6.1
- **6.1-3** (MUST) When a resource stops being a member of a locked collection
  it must no longer be indirectly locked by that lock. RFC4918§6.1
- **6.1-4** (MUST) If a request causes the lock-root of any lock to become an
  unmapped URL, that request must also delete the lock. RFC4918§6.1
- **6.2-1** (MUST) A successful request for a new shared lock must generate a
  unique lock, and lock token, associated with the requesting principal.
  RFC4918§6.2
- **6.4-1** (MUST) When a locked resource is modified, the server must check
  that the authenticated principal matches the lock creator, in addition to
  checking for valid lock token submission. RFC4918§6.4
- **6.4-2** (MUST) Write access and other privileges must be enforced through
  normal privilege or authentication mechanisms, not through the obscurity of
  lock token values. RFC4918§6.4
- **6.5-1** (MUST) Lock token URIs must be unique across all resources for all
  time. RFC4918§6.5
- **6.6-1** (MUST) The lock timeout counter must be restarted when a refresh
  LOCK request succeeds. RFC4918§6.6
- **6.6-2** (SHOULD NOT) The timeout counter should not be restarted at any
  other time. RFC4918§6.6
- **6.6-3** (SHOULD) When the timeout expires the lock should be removed, the
  server acting as if UNLOCK had been executed. RFC4918§6.6
- **6.7-1** (MUST) Any DAV-compliant resource supporting LOCK must support the
  `DAV:supportedlock` property. RFC4918§6.7
- **6.8-1** (MUST) Any DAV-compliant resource supporting LOCK must support the
  `DAV:lockdiscovery` property. RFC4918§6.8

## 7. Write Lock

- **7.3-1** (MUST) A successful LOCK on an unmapped URL must create a locked,
  non-collection resource with empty content. RFC4918§7.3
- **7.3-2** (SHOULD NOT) Such a resource should not disappear when its lock goes
  away. RFC4918§7.3
- **7.3-3** (MUST NOT) Such a resource must not be converted into a collection;
  the server must fail a MKCOL request against it. RFC4918§7.3
- **7.3-4** (MUST) Such a resource must have defined values for
  `DAV:lockdiscovery` and `DAV:supportedlock`. RFC4918§7.3
- **7.3-5** (MUST) The response to a LOCK that creates such a resource must
  indicate creation with 201 Created, and must still include the
  `DAV:lockdiscovery` property in the body. RFC4918§7.3
- **7.4-1** (MUST) A depth-infinity LOCK on a collection containing a
  conflicting locked member must fail with 423 (Locked). RFC4918§7.4
- **7.4-2** (SHOULD) That 423 response should contain the `no-conflicting-lock`
  precondition element. RFC4918§7.4
- **7.4-3** (MUST) A resource whose URL is added as an internal member of a
  depth-infinity locked collection must be automatically protected by that lock.
  RFC4918§7.4
- **7.5-1** (MUST) A lock token must be submitted by an authorized principal for
  every locked resource a method may change, or the method must fail.
  RFC4918§7.5
- **7.6-1** (MUST NOT) A COPY must not duplicate any write lock active on the
  source resource. RFC4918§7.6
- **7.6-2** (MUST NOT) A successful MOVE must not move the write lock along with
  the resource. RFC4918§7.6
- **7.6-3** (MUST) If a lock exists at the MOVE destination, the server must add
  the moved resource to the destination lock's scope. RFC4918§7.6
- **7.7-1** (MUST NOT) A server receiving a LOCK request with no body must not
  create a new lock; such a request refreshes an existing lock, and must at
  minimum reset any timers associated with it. RFC4918§7.7

## 8. General Request and Response Handling

- **8.1-1** (MUST) Servers must return authorization errors in preference to
  other errors, to avoid leaking the existence of protected resources.
  RFC4918§8.1
- **8.2-1** (SHOULD) When XML is used for a request or response body, the
  `Content-Type` should be `application/xml`; `text/xml` is deprecated.
  RFC4918§8.2
- **8.2-2** (MUST) Implementations must accept both `text/xml` and
  `application/xml` in request and response bodies. RFC4918§8.2
- **8.2-3** (MUST) All XML used in requests or responses must be at minimum
  well-formed and use namespaces correctly. RFC4918§8.2
- **8.2-4** (MUST) If a server receives XML that is not well-formed it must
  reject the entire request with 400 (Bad Request). RFC4918§8.2
- **8.3-1** (MUST) A server must ensure every `href` value within a Multi-Status
  response uses the same format — either all relative references or all full
  URIs. RFC4918§8.3
- **8.3-2** (MUST NOT) Within `Simple-ref` productions (Multi-Status `href`
  values, and the `Destination` and `If` header URLs) senders must not use
  dot-segments, nor prefixes that do not match the Request-URI. RFC4918§8.3
- **8.3-3** (SHOULD) Identifiers for collections should end in a '/' character.
  RFC4918§8.3
- **8.4-1** (MUST) Servers must examine all requests for a body, even when a
  body was not expected. RFC4918§8.4
- **8.4-2** (MUST) Where a request body is present but would be ignored, the
  server must reject the request with 415 (Unsupported Media Type).
  RFC4918§8.4
- **8.5-1** (MUST) The server must perform authorization checks before checking
  any HTTP conditional header. RFC4918§8.5
- **8.6-1** (SHOULD NOT) A WebDAV server should not change the ETag, or the
  Last-Modified time, for a resource whose body and location are unchanged.
  RFC4918§8.6
- **8.8-1** (MUST) For any given URL, the `Last-Modified` value must increment
  every time the representation returned by GET changes, within the limits of
  timestamp resolution. RFC4918§8.8
- **8.8-2** (MUST NOT) For any given URL, an ETag value must not be reused for
  different representations returned by GET. RFC4918§8.8

## 9.1. PROPFIND Method

- **9.1-1** (MUST) All DAV-compliant resources must support PROPFIND, the
  `propfind` XML element, and all XML elements defined for use with it.
  RFC4918§9.1
- **9.1-2** (MUST) Servers must support Depth "0" and "1" PROPFIND requests on
  WebDAV-compliant resources. RFC4918§9.1
- **9.1-3** (SHOULD) Servers should support Depth "infinity" PROPFIND requests,
  though support may be disabled for performance and security reasons.
  RFC4918§9.1
- **9.1-4** (SHOULD) Servers should treat a PROPFIND request without a Depth
  header as if `Depth: infinity` had been included. RFC4918§9.1
- **9.1-5** (MUST) An empty PROPFIND request body must be treated as if it were
  an `allprop` request. RFC4918§9.1
- **9.1-6** (MUST) All servers must support returning a `text/xml` or
  `application/xml` response containing a `multistatus` XML element describing
  the results. RFC4918§9.1
- **9.1-7** (MUST) If there is an error retrieving a property, a proper error
  result must be included in the response. RFC4918§9.1
- **9.1-8** (MUST) A request for the value of a property that does not exist is
  an error, and must be noted with a `response` element containing a 404 (Not
  Found) status. RFC4918§9.1
- **9.1-9** (MUST) The `multistatus` element for a collection must include a
  `response` element for each member URL of the collection, to the depth
  requested. RFC4918§9.1
- **9.1-10** (SHOULD NOT) It should not include `response` elements for
  resources that are not WebDAV-compliant. RFC4918§9.1
- **9.1-11** (MUST) Each `response` element must contain an `href` element
  giving the URL of the resource whose properties are reported. RFC4918§9.1
- **9.1.1-1** (SHOULD) A server that rejects a Depth-infinity PROPFIND with 403
  should use the `propfind-finite-depth` precondition code in the error body.
  RFC4918§9.1.1

## 9.2. PROPPATCH Method

- **9.2-1** (MUST) All DAV-compliant resources must support PROPPATCH and must
  process instructions specified using the `propertyupdate`, `set` and `remove`
  XML elements. RFC4918§9.2
- **9.2-2** (SHOULD) DAV-compliant resources should support the setting of
  arbitrary dead properties. RFC4918§9.2
- **9.2-3** (MUST) The request body of a PROPPATCH must contain the
  `propertyupdate` XML element, so a server must reject a request that does not.
  RFC4918§9.2
- **9.2-4** (MUST) Servers must process PROPPATCH instructions in document
  order, an explicit exception to the normal rule that ordering is irrelevant.
  RFC4918§9.2
- **9.2-5** (MUST) PROPPATCH instructions must either all be executed or none
  executed; if any error occurs, all executed instructions must be undone and a
  proper error result returned. RFC4918§9.2
- **9.2-6** (MUST) If a server attempts to make any of the property changes in a
  PROPPATCH request, the response must be a Multi-Status response. RFC4918§9.2
- **9.2-7** (MUST NOT) Responses to PROPPATCH must not be cached. RFC4918§9.2
- **9.2.1-1** (SHOULD) When returning 403 because the client attempted to set a
  protected property, the server should use the
  `cannot-modify-protected-property` precondition code. RFC4918§9.2.1

## 9.3. MKCOL Method

- **9.3-1** (MUST) If the Request-URI is already mapped to a resource, MKCOL
  must fail. RFC4918§9.3
- **9.3-2** (MUST) During MKCOL processing the server must make the Request-URI
  an internal member of its parent collection, unless the Request-URI is "/";
  if no such ancestor exists the method must fail. RFC4918§9.3
- **9.3-3** (MUST) All ancestors must already exist, or MKCOL must fail with 409
  (Conflict). RFC4918§9.3
- **9.3-4** (SHOULD) When MKCOL is invoked without a request body, the newly
  created collection should have no members. RFC4918§9.3
- **9.3-5** (MUST) If the server receives a MKCOL request entity type it does not
  support or understand, it must respond with 415 (Unsupported Media Type).
  RFC4918§9.3
- **9.3-6** (MUST NOT) Responses to MKCOL must not be cached. RFC4918§9.3
- **9.3.1-1** (MUST NOT) When returning 409 because intermediate collections are
  missing, the server must not create those intermediate collections
  automatically. RFC4918§9.3.1

## 9.6. DELETE Requirements

- **9.6-1** (MUST) DELETE must destroy locks rooted on the deleted resource.
  RFC4918§9.6
- **9.6-2** (MUST) DELETE must remove the mapping from the Request-URI to any
  resource. RFC4918§9.6
- **9.6-3** (MUST) After a successful DELETE, a subsequent GET, HEAD or PROPFIND
  on the target Request-URI must return 404 (Not Found). RFC4918§9.6
- **9.6.1-1** (MUST) DELETE on a collection must act as if `Depth: infinity` had
  been used. RFC4918§9.6.1
- **9.6.1-2** (MUST NOT) If any member resource cannot be deleted, none of that
  member's ancestors must be deleted, so as to maintain URL namespace
  consistency. RFC4918§9.6.1
- **9.6.1-3** (MUST) Any headers included with DELETE must be applied in
  processing every resource to be deleted. RFC4918§9.6.1
- **9.6.1-4** (MUST) When DELETE has completed processing it must result in a
  consistent URL namespace. RFC4918§9.6.1
- **9.6.1-5** (SHOULD NOT) 424 (Failed Dependency) status codes should not
  appear in the 207 (Multi-Status) response for DELETE. RFC4918§9.6.1
- **9.6.1-6** (SHOULD NOT) 204 (No Content) should not be returned in the 207,
  since it is the default success code. RFC4918§9.6.1

## 9.7. PUT Requirements

- **9.7.1-1** (MUST) A PUT that would create a resource without an appropriately
  scoped parent collection must fail with 409 (Conflict). RFC4918§9.7.1

## 9.8. COPY Method

- **9.8-1** (MUST) The `Destination` header must be present on a COPY request,
  so a server must reject a COPY without one. RFC4918§9.8
- **9.8-2** (MUST) All WebDAV-compliant resources must support the COPY method.
  RFC4918§9.8
- **9.8-3** (MUST NOT) Responses to COPY must not be cached. RFC4918§9.8
- **9.8.2-1** (SHOULD) After a successful COPY, all dead properties on the
  source should be duplicated on the destination. RFC4918§9.8.2
- **9.8.2-2** (SHOULD) Live properties defined in this document should be
  duplicated as identically behaving live properties at the destination, though
  not necessarily with the same values. RFC4918§9.8.2
- **9.8.2-3** (SHOULD NOT) Servers should not convert live properties into dead
  properties on the destination resource. RFC4918§9.8.2
- **9.8.3-1** (MUST) COPY on a collection without a Depth header must act as if
  `Depth: infinity` had been included. RFC4918§9.8.3
- **9.8.3-2** (MUST) Servers must support the "0" and "infinity" Depth header
  behaviours for COPY on WebDAV-compliant resources. RFC4918§9.8.3
- **9.8.3-3** (MUST) Any headers included with a COPY must be applied in
  processing every resource copied, with the exception of `Destination`.
  RFC4918§9.8.3
- **9.8.3-4** (MUST) When COPY has completed processing it must have created a
  consistent URL namespace at the destination. RFC4918§9.8.3
- **9.8.3-5** (MUST NOT) If an error occurs while copying an internal
  collection, the server must not copy any resources identified by members of
  that collection. RFC4918§9.8.3
- **9.8.3-6** (SHOULD) After detecting an error, COPY should try to finish as
  much of the original copy operation as possible. RFC4918§9.8.3
- **9.8.3-7** (MUST) If an error occurs with a resource other than the one
  identified by the Request-URI, the response must be 207 (Multi-Status) and the
  URL of the failing resource must appear with the specific error. RFC4918§9.8.3
- **9.8.3-8** (SHOULD NOT) 424 (Failed Dependency) should not be returned in a
  207 response from COPY. RFC4918§9.8.3
- **9.8.3-9** (SHOULD NOT) 201 (Created) and 204 (No Content) should not be
  returned as values in a 207 response from COPY. RFC4918§9.8.3
- **9.8.4-1** (MUST) If a COPY has `Overwrite: F` and a resource exists at the
  Destination URL, the server must fail the request. RFC4918§9.8.4
- **9.8.4-2** (MUST) When a collection is overwritten, the membership of the
  destination collection after the COPY must equal the membership of the source
  collection immediately before it — merging the two is not compliant.
  RFC4918§9.8.4
- **9.8.5-1** (MUST NOT) When returning 409 because intermediate collections are
  missing at the destination, the server must not create them automatically.
  RFC4918§9.8.5
- **9.8.5-2** (SHOULD) A 423 (Locked) response from COPY should contain the
  `lock-token-submitted` precondition element. RFC4918§9.8.5

## 9.9. MOVE Method

- **9.9-1** (MUST) The `Destination` header must be present on all MOVE
  requests, and MOVE must follow all COPY requirements for the copy part of the
  operation. RFC4918§9.9
- **9.9-2** (MUST) All WebDAV-compliant resources must support the MOVE method.
  RFC4918§9.9
- **9.9-3** (MUST NOT) Responses to MOVE must not be cached. RFC4918§9.9
- **9.9.1-1** (SHOULD) Live properties should be moved along with the resource,
  so that it has identically behaving live properties at the destination.
  RFC4918§9.9.1
- **9.9.1-2** (SHOULD) The `DAV:creationdate` property value should remain the
  same after a MOVE. RFC4918§9.9.1
- **9.9.1-3** (MUST) Dead properties must be moved along with the resource.
  RFC4918§9.9.1
- **9.9.2-1** (MUST) MOVE on a collection must act as if `Depth: infinity` had
  been used. RFC4918§9.9.2
- **9.9.2-2** (MUST) Any headers included with MOVE must be applied in
  processing every resource moved, with the exception of `Destination`.
  RFC4918§9.9.2
- **9.9.2-3** (MUST) When MOVE has completed processing it must have created a
  consistent URL namespace at both source and destination. RFC4918§9.9.2
- **9.9.2-4** (MUST NOT) If an error occurs while moving an internal collection,
  the server must not move any resources identified by members of the failed
  collection. RFC4918§9.9.2
- **9.9.2-5** (SHOULD) After detecting an error, MOVE should try to finish as
  much of the original move as possible. RFC4918§9.9.2
- **9.9.2-6** (MUST) If an error occurs with a resource other than the one
  identified by the Request-URI, the response must be 207 (Multi-Status) and the
  errored resource's URL must appear with the specific error. RFC4918§9.9.2
- **9.9.2-7** (SHOULD NOT) 424 (Failed Dependency) should not be returned in a
  207 response from MOVE. RFC4918§9.9.2
- **9.9.2-8** (SHOULD NOT) 201 (Created) and 204 (No Content) should not be
  returned as values in a 207 response from MOVE. RFC4918§9.9.2
- **9.9.3-1** (MUST) If a resource exists at the destination and `Overwrite` is
  "T", the server must perform a `Depth: infinity` DELETE on the destination
  before performing the move. RFC4918§9.9.3
- **9.9.4-1** (MUST NOT) When returning 409 because intermediate collections are
  missing at the destination, the server must not create them automatically.
  RFC4918§9.9.4
- **9.9.4-2** (SHOULD) A 423 (Locked) response from MOVE should contain the
  `lock-token-submitted` precondition element. RFC4918§9.9.4

## 9.10. LOCK Method

- **9.10-1** (MUST) Any resource supporting LOCK must at minimum support the XML
  request and response formats defined in the specification. RFC4918§9.10
- **9.10-2** (MUST NOT) Responses to LOCK must not be cached. RFC4918§9.10
- **9.10.1-1** (MUST) A LOCK request that creates a new lock must have an XML
  request body, so a server must reject one that does not. RFC4918§9.10.1
- **9.10.1-2** (MUST) The server must preserve the information provided by the
  client in the `owner` element of the LOCK request. RFC4918§9.10.1
- **9.10.1-3** (MUST) A successful LOCK response must contain a body with the
  value of the `DAV:lockdiscovery` property in a `prop` element, carrying full
  information about the lock just granted. RFC4918§9.10.1
- **9.10.1-4** (MUST) A successful LOCK response must include the `Lock-Token`
  response header with the token of the new lock. RFC4918§9.10.1
- **9.10.2-1** (MUST) A refresh LOCK request must have no body and must identify
  the lock to refresh via an `If` header carrying a single lock token.
  RFC4918§9.10.2
- **9.10.2-2** (MUST) A server must ignore the Depth header on a LOCK refresh.
  RFC4918§9.10.2
- **9.10.2-3** (MUST) The response body of a successful refresh LOCK must
  contain the new value of the `DAV:lockdiscovery` property. RFC4918§9.10.2
- **9.10.3-1** (MUST NOT) Depth values other than 0 or infinity must not be used
  with the LOCK method, so a server must reject them. RFC4918§9.10.3
- **9.10.3-2** (MUST) All resources that support LOCK must support the Depth
  header. RFC4918§9.10.3
- **9.10.3-3** (MUST) A successful Depth-infinity LOCK must return a single lock
  token covering the whole hierarchy; partial success is not an option for LOCK
  or UNLOCK. RFC4918§9.10.3
- **9.10.3-4** (MUST) If the lock cannot be granted to all resources, the server
  must return a Multi-Status response with a `response` element for at least one
  resource that prevented the lock, with a suitable status code. RFC4918§9.10.3
- **9.10.3-5** (SHOULD) If the resource causing the failure was not the
  Request-URI, the server should also include a `response` element for the
  Request-URI with a 424 (Failed Dependency) status. RFC4918§9.10.3
- **9.10.3-6** (MUST) If no Depth header is submitted on a LOCK request, the
  request must act as if `Depth: infinity` had been submitted. RFC4918§9.10.3
- **9.10.4-1** (MUST) A successful LOCK on a URL where no resource previously
  existed must create an empty, locked, non-collection resource. RFC4918§9.10.4
- **9.10.4-2** (MUST) Such empty resources must appear in PROPFIND responses
  that include that URL in scope. RFC4918§9.10.4
- **9.10.4-3** (MUST) A server must respond successfully to a GET on such an
  empty resource, using either 204 (No Content) or 200 (OK) with a
  `Content-Length` of zero. RFC4918§9.10.4
- **9.10.5-1** (MUST NOT) A lock must not be granted where the lock
  compatibility table gives "False": an exclusive lock request against a
  resource holding any lock, and a shared lock request against an exclusively
  locked resource. RFC4918§9.10.5
- **9.10.6-1** (MUST NOT) When LOCK returns 409 because intermediate collections
  are missing, the server must not create them automatically. RFC4918§9.10.6

## 9.11. UNLOCK Method

- **9.11-1** (MUST) The Request-URI of an UNLOCK must identify a resource within
  the scope of the lock, so a server must reject one that does not.
  RFC4918§9.11
- **9.11-2** (MUST) For a successful response, the server must delete the lock
  entirely. RFC4918§9.11
- **9.11-3** (MUST) If all resources locked under the submitted lock token
  cannot be unlocked, the UNLOCK request must fail. RFC4918§9.11
- **9.11-4** (MUST) Any DAV-compliant resource that supports LOCK must support
  UNLOCK. RFC4918§9.11
- **9.11-5** (MUST NOT) Responses to UNLOCK must not be cached. RFC4918§9.11

## 10. HTTP Headers for Distributed Authoring

- **10.1-1** (MUST) All DAV-compliant resources must return the `DAV` header
  with compliance class "1" on all OPTIONS responses. RFC4918§10.1
- **10.1-2** (SHOULD NOT) Where WebDAV is supported only in part of the server
  namespace, an OPTIONS request to a non-WebDAV resource, including "/", should
  not advertise WebDAV support. RFC4918§10.1
- **10.1-3** (SHOULD) Compliance class identifiers not standardised through the
  IETF RFC process should be Coded-URLs, to encourage uniqueness. RFC4918§10.1
- **10.2-1** (MUST) Each header on a request carrying a Depth header must be
  applied only to the Request-URI if it applies to any resource, unless specific
  Depth behaviour is defined for that header. RFC4918§10.2
- **10.2-2** (MUST) If a resource has no internal members, the Depth header must
  be ignored. RFC4918§10.2
- **10.3-1** (MUST) If the `Destination` value is an absolute-URI naming a
  different server, and the source server cannot attempt a copy to that remote
  server, it must fail the request. RFC4918§10.3
- **10.3-2** (SHOULD) If the `Destination` value is too long or otherwise
  unacceptable, the server should return 400 (Bad Request), ideally with an
  informative error body. RFC4918§10.3
- **10.4.1-1** (MUST) If an `If` header is evaluated and all of its state lists
  fail, the request must fail with 412 (Precondition Failed). RFC4918§10.4.1
- **10.4.3-1** (MUST) If the `If` header evaluates to false the server must
  reject the request with 412; otherwise execution proceeds as if the header
  were not present. RFC4918§10.4.3
- **10.4.4-1** (MUST) When matching entity tags in an `If` header, servers must
  use either the weak or the strong comparison function. RFC4918§10.4.4
- **10.5-1** (MUST) The lock token in the `Lock-Token` request header must
  identify a lock that contains the Request-URI resource as a member.
  RFC4918§10.5
- **10.6-1** (MUST) If the `Overwrite` header is absent from a COPY or MOVE, the
  resource must treat the request as if `Overwrite: T` had been given.
  RFC4918§10.6
- **10.6-2** (MUST) If a COPY or MOVE is not performed because of the
  `Overwrite` header value, the method must fail with 412 (Precondition Failed).
  RFC4918§10.6
- **10.6-3** (MUST) The server must perform authorization checks before checking
  the `Overwrite` header or any other conditional header. RFC4918§10.6
- **10.6-4** (MUST) All DAV-compliant resources must support the `Overwrite`
  header. RFC4918§10.6
- **10.7-1** (MUST NOT) The timeout value for TimeType "Second" must not be
  greater than 2^32-1. RFC4918§10.7

## 11–13. Status Codes and Multi-Status

- **11-1** (SHOULD) A 423 (Locked) response should contain an appropriate
  precondition or postcondition code, such as `lock-token-submitted` or
  `no-conflicting-lock`. RFC4918§11
- **12-1** (MUST NOT) A 300-level redirect response must not be used when the
  server has created a new resource in response to the request. RFC4918§12
- **12-2** (MUST) If the server evaluates a conditional header and the condition
  fails to hold, 412 (Precondition Failed) must be returned. RFC4918§12
- **12-3** (MUST NOT) If the client did not include a conditional header, the
  server must not use the 412 status code. RFC4918§12
- **13-1** (SHOULD NOT) 100-series status codes should not be recorded in a
  `response` XML element. RFC4918§13
- **13-2** (MUST) Each `response` element must have an `href` element
  identifying the resource. RFC4918§13
- **13.2-1** (MUST) Servers must use the `location` element with redirect
  responses inside a Multi-Status. RFC4918§13.2

## 14. XML Element Definitions

- **14.3-1** (MUST) The `DAV:resourcetype` property of a collection resource
  must contain the `DAV:collection` element. RFC4918§14.3
- **14.5-1** (MUST NOT) The `error` element must contain at least one XML
  element and must not contain text or mixed content. RFC4918§14.5
- **14.7-1** (MUST) The `href` element must contain a URI or a relative
  reference. RFC4918§14.7
- **14.8-1** (MUST NOT) The `include` element must not contain text or mixed
  content. RFC4918§14.8
- **14.12-1** (SHOULD) The server should include the `lockroot` element in all
  `DAV:lockdiscovery` property values and in LOCK responses. RFC4918§14.12
- **14.17-1** (MUST) The `owner` value must be treated as a dead property for
  purposes of XML Information Item preservation. RFC4918§14.17
- **14.17-2** (MUST NOT) The server must not alter the `owner` value unless the
  value provided by the client is empty. RFC4918§14.17
- **14.18-1** (MUST NOT) The `prop` element must not contain text or mixed
  content, and all elements inside it must define properties related to the
  resource. RFC4918§14.18
- **14.22-1** (MUST) The `propstat` element must contain exactly one `prop`
  element and one `status` element, and the `prop` element must list only
  property names. RFC4918§14.22
- **14.24-1** (MUST NOT) A particular `href` value must not appear more than
  once as the child of a `response` element under a `multistatus` element.
  RFC4918§14.24
- **14.26-1** (MUST) Language tagging information in the scope of a `prop`
  element inside `set` (the `xml:lang` attribute) must be persistently stored
  with the property and must be subsequently retrievable using PROPFIND.
  RFC4918§14.26

## 15. DAV Properties

- **15-1** (SHOULD) Server implementers should strip linear whitespace from
  `DAV:get*` header-derived values before using them as property values.
  RFC4918§15
- **15.1-1** (SHOULD) The `DAV:creationdate` property should be defined on all
  DAV-compliant resources. RFC4918§15.1
- **15.1-2** (SHOULD) Servers incapable of persistently recording the creation
  date should leave `DAV:creationdate` undefined, reporting "Not Found", rather
  than inventing a value. RFC4918§15.1
- **15.1-3** (SHOULD) The `DAV:creationdate` value should be kept during a MOVE.
  RFC4918§15.1
- **15.2-1** (SHOULD NOT) `DAV:displayname` should not be protected, so that
  clients can set it. RFC4918§15.2
- **15.2-2** (SHOULD) The `DAV:displayname` value should be preserved in COPY
  and MOVE operations, and should have the same value independent of the
  Request-URI used to retrieve it. RFC4918§15.2
- **15.3-1** (MUST) `DAV:getcontentlanguage` must be defined on any
  DAV-compliant resource that returns the `Content-Language` header on a GET.
  RFC4918§15.3
- **15.3-2** (SHOULD NOT) `DAV:getcontentlanguage` should not be protected, so
  that clients can reset the language. RFC4918§15.3
- **15.3-3** (SHOULD) Its value should be preserved in COPY and MOVE operations.
  RFC4918§15.3
- **15.4-1** (MUST) `DAV:getcontentlength` must be defined on any DAV-compliant
  resource that returns the `Content-Length` header in response to a GET.
  RFC4918§15.4
- **15.5-1** (MUST) `DAV:getcontenttype` must be defined on any DAV-compliant
  resource that returns the `Content-Type` header in response to a GET.
  RFC4918§15.5
- **15.5-2** (SHOULD) Its value should be preserved in COPY and MOVE operations.
  RFC4918§15.5
- **15.6-1** (MUST) `DAV:getetag` must be defined on any DAV-compliant resource
  that returns the `ETag` header. RFC4918§15.6
- **15.6-2** (MUST) `DAV:getetag` must be protected, since the value is created
  and controlled by the server. RFC4918§15.6
- **15.7-1** (MUST) `DAV:getlastmodified` must be defined on any DAV-compliant
  resource that returns the `Last-Modified` header in response to a GET.
  RFC4918§15.7
- **15.7-2** (MUST) Its value must be an `rfc1123-date`, per the property's
  `Value:` production read together with **4.1-1**. RFC4918§15.7
- **15.7-3** (SHOULD) `DAV:getlastmodified` should be protected. RFC4918§15.7
- **15.7-4** (SHOULD NOT) The last-modified date should only reflect changes to
  the body of the resource; a change to a property alone should not change it.
  RFC4918§15.7
- **15.8-1** (MUST) `DAV:lockdiscovery` must be protected — clients change the
  list of locks through LOCK and UNLOCK, not PROPPATCH. RFC4918§15.8
- **15.9-1** (MUST) `DAV:resourcetype` must be defined on all DAV-compliant
  resources. RFC4918§15.9
- **15.9-2** (MUST NOT) The `DAV:resourcetype` element must not contain text or
  mixed content. RFC4918§15.9
- **15.9-3** (SHOULD) `DAV:resourcetype` should be protected. RFC4918§15.9
- **15.10-1** (MUST) `DAV:supportedlock` must be protected — servers, not
  clients, determine which lock mechanisms are supported. RFC4918§15.10

## 16. Precondition/Postcondition XML Elements

- **16-1** (MUST) In a 207 Multi-Status response, a precondition or
  postcondition XML element must appear inside an `error` element in the
  appropriate `propstat` or `response` element. RFC4918§16
- **16-2** (MUST) In other error responses using this specification's `error`
  body, the precondition/postcondition element must be returned as the child of
  a top-level `error` element. RFC4918§16
- **16-3** (SHOULD) A server supporting this specification should use the XML
  error body whenever a precondition or postcondition defined in the document is
  violated. RFC4918§16
- **16-4** (SHOULD) If an UNLOCK Request-URI does not fall within the scope of
  the lock identified by the `Lock-Token` header, the server should use the
  `lock-token-matches-request-uri` error. RFC4918§16
- **16-5** (MUST) A `lock-token-submitted` element, if present, must contain at
  least one URL of a locked resource that prevented the request. RFC4918§16

## 17. XML Extensibility in DAV

- **17-1** (MUST) Servers must process received XML documents as if unexpected
  elements and attributes, and all children of unrecognised elements, were not
  there. RFC4918§17
- **17-2** (MUST) When setting dead DAV properties, the server must record all
  XML elements — the "ignore unexpected elements" rule does not apply.
  RFC4918§17
- **17-3** (SHOULD) Processing instructions in XML should be ignored by
  recipients. RFC4918§17
- **17-4** (MUST NOT) A recipient of a WebDAV message with an XML body must not
  validate the document against any hard-coded or dynamically-declared DTD.
  RFC4918§17

## 18. DAV Compliance Classes

- **18.1-1** (MUST) Class 1 compliant resources must return, at minimum, the
  value "1" in the `DAV` header on all OPTIONS responses. RFC4918§18.1
- **18.2-1** (MUST) A class 2 compliant resource must meet all class 1
  requirements and support the LOCK method, the `DAV:supportedlock` and
  `DAV:lockdiscovery` properties, the Timeout response header and the
  `Lock-Token` request header. RFC4918§18.2
- **18.2-2** (SHOULD) A class 2 compliant resource should also support the
  `Timeout` request header and the `owner` XML element. RFC4918§18.2
- **18.2-3** (MUST) Class 2 compliant resources must return, at minimum, the
  values "1" and "2" in the `DAV` header on all OPTIONS responses. RFC4918§18.2
- **18.3-1** (MUST) A resource advertising class 3 compliance must support class
  1 as well. RFC4918§18.3

## 19–20. Internationalization and Security

- **19-1** (MUST) WebDAV applications must support the character set tagging,
  character set encoding and language tagging functionality of the XML
  specification. RFC4918§19
- **20.1-1** (MUST NOT) Basic authentication must not be used to authenticate a
  WebDAV client to a server unless the connection is secure. RFC4918§20.1
- **20.1-2** (MUST NOT) A WebDAV server must not send a Basic authentication
  challenge in a `WWW-Authenticate` header unless the connection is secure.
  RFC4918§20.1
- **20.1-3** (MUST) WebDAV applications must support the Digest authentication
  scheme. RFC4918§20.1
- **20.6-1** (SHOULD) If a server chooses not to handle external XML entities,
  it should respond to requests containing them with the
  `no-external-entities` condition code. RFC4918§20.6
